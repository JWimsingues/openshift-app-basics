Time: 50 minutes.

You set CPU and memory requests and limits on the web container.
You add a readiness probe and a liveness probe.
The Pod stays not Ready until the readiness probe passes.

== Prerequisites

* xref:04-config.adoc[Lab 4] is complete
* The ConfigMap, Secret, Service, and Route still exist
* You are in the repository root

== How it works

A request is what the scheduler reserves.
A limit is the maximum the container can use.
A readiness probe decides if the Pod should receive Service traffic.
A liveness probe decides if the kubelet should restart the container.
The readiness probe waits 15 seconds before the first check.
During that wait the Pod stays `0/1`.

== Steps to apply

[#resources]
=== 1. Set requests and limits

*What:* Apply the Deployment that requests 100m CPU and 128Mi memory, and limits the container to 300m CPU and 256Mi memory.

*Why:* The scheduler needs the request. The limit stops one container from taking the node.

The same file also adds the probes. The next step watches those probes.
Apply the file once.

icon:clock[] ~20 seconds (readiness waits 15 seconds, then the probe runs)

[.console-input]
[source,bash]
----
oc apply -f 05-resources/deployment.yaml -n "${WORKSHOP_NAMESPACE}" --context cluster
oc get pods -l app=workshop-web -n "${WORKSHOP_NAMESPACE}" --context cluster
----

.Verify: The containers show the new limits
[%collapsible]
====
[.console-input]
[source,bash]
----
oc describe pod -l app=workshop-web -n "${WORKSHOP_NAMESPACE}" --context cluster | grep -A 4 "Limits:"
----

[.console-output]
[source,bash]

      cpu:     300m
      memory:  256Mi
    Requests:
      cpu:     100m

[#probes]
=== 2. Watch the probes

*What:* Wait until the readiness probe passes, then confirm both Pods are Ready.

*Why:* A Pod that fails readiness stays out of the Service. A failed liveness probe restarts the container.

icon:clock[] ~20 seconds

[.console-input]
[source,bash]
----
oc rollout status deployment/workshop-web -n "${WORKSHOP_NAMESPACE}" --context cluster
oc get pods -l app=workshop-web -n "${WORKSHOP_NAMESPACE}" --context cluster
----

.Verify: Both Pods show 1/1 Ready
[%collapsible]
====
[.console-output]
[source,bash]
----
NAME                            READY   STATUS    RESTARTS   AGE
workshop-web-6b8d4c9f7a-aaaaa   1/1     Running   0          40s
workshop-web-6b8d4c9f7a-bbbbb   1/1     Running   0          40s
----
====

If you ran `oc get pods` in step 1 before 15 seconds, `READY` was `0/1`.
That was the readiness probe waiting. It is the result this lab asks you to see.

== Alternatives considered

[cols="2,4",options="header"]
|===
| Approach | Notes

| Requests, limits, httpGet probes
| Chosen. `httpGet` on `/` checks that httpd serves the ConfigMap page.

| A TCP probe only
| Proves the port is open. It does not prove that `/` returns the page.

| No limits
| The quota still caps the namespace. One container can still starve another Pod.
|===
